# JsExec Module Loading System

**Date**: 2026-01-20
**Status**: Implemented
**Components**: jsexec, substrate

## Context

JsExec executes JavaScript code in ephemeral Cloudflare workerd V8 isolates. Each execution spawns a fresh workerd process with user code embedded directly, providing complete isolation. Previously, executions only had access to standard JavaScript globals (Math, JSON, Date, etc.) and a custom console wrapper. There was no way to provide shared libraries or utility functions across executions.

## Problem Statement

Users need to:
1. Load external JavaScript libraries (e.g., lodash, TypeScript compiler, custom utilities)
2. Share common code across multiple executions without re-embedding it each time
3. Access libraries both via imports and optionally via `globalThis`
4. Support both inline code and file-based modules

The ephemeral process model means we can't use persistent state - modules must be embedded in the workerd configuration at spawn time.

## Solution Design

### Architecture

```
┌─────────────────────────────────────────────────────┐
│ JsExecConfig                                        │
│  └─ modules: Vec<ModuleConfig>                     │
│      ├─ name: String                               │
│      ├─ source: Code(String) | Path(PathBuf)       │
│      └─ expose_global: bool                        │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│ RunnerConfig (execution time)                       │
│  └─ modules: Vec<ModuleConfig>                     │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│ Module Resolution                                   │
│  ├─ Load inline code from ModuleSource::Code       │
│  └─ Read file from ModuleSource::Path              │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│ Workerd Process Setup (per execution)              │
│  ├─ Write each module to temp dir: {name}.js       │
│  ├─ Generate Cap'n Proto config with module list   │
│  └─ Embed all modules in worker configuration      │
└─────────────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────────────┐
│ Worker Module Generation                            │
│  ├─ Generate imports: import * as {name} from ...  │
│  ├─ Expose on globalThis if configured             │
│  └─ Create ctx.modules object                      │
└─────────────────────────────────────────────────────┘
```

### Key Components

#### 1. Configuration Types (`types.rs`)

```rust
pub struct ModuleConfig {
    pub name: String,
    pub source: ModuleSource,
    pub expose_global: bool,
}

pub enum ModuleSource {
    Code(String),
    Path(PathBuf),
}
```

**Builder pattern**:
```rust
ModuleConfig::inline("utils", code)
ModuleConfig::from_file("lodash", "/path/to/lodash.js")
    .with_global(true)
```

#### 2. Module Resolution (`runner.rs`)

```rust
pub struct ResolvedModule {
    pub name: String,
    pub code: String,
    pub expose_global: bool,
}

impl ResolvedModule {
    pub async fn resolve(config: &ModuleConfig) -> Result<Self, std::io::Error>
}
```

Resolution happens at execution time:
- `ModuleSource::Code` → Use inline code directly
- `ModuleSource::Path` → Read file with `tokio::fs::read_to_string`

#### 3. Workerd Configuration Generation

**Module entries in Cap'n Proto config**:
```capnp
const mainWorker :Workerd.Worker = (
  modules = [
    (name = "worker", esModule = embed "worker.js"),
    (name = "utils", esModule = embed "utils.js"),
    (name = "lodash", esModule = embed "lodash.js")
  ],
  compatibilityDate = "2024-01-01",
);
```

Each module file is written to the temp directory alongside the main worker module.

#### 4. Worker Module Generation

Generated imports at top of worker.js:
```javascript
import * as utils from 'utils';
import * as lodash from 'lodash';
```

Optional globalThis exposure:
```javascript
globalThis.utils = utils.default || utils;
```

Context object with modules:
```javascript
const MODULES = {
  utils: utils.default || utils,
  lodash: lodash.default || lodash
};

const ctx = { ...CTX.data, modules: MODULES };
```

### Access Patterns

User code can access modules in two ways:

#### 1. Via `ctx.modules` (always available)
```javascript
const result = ctx.modules.utils.add(10, 20);
return result;
```

#### 2. Via `globalThis` (if `expose_global: true`)
```javascript
const result = utils.add(10, 20);
return result;
```

## Implementation Details

### File Locations

- **Types**: `jsexec/src/types.rs`
  - `ModuleConfig`, `ModuleSource`
  - Added to `JsExecConfig.modules`

- **Runner**: `jsexec/src/runner.rs`
  - `ResolvedModule` struct
  - `resolve()` async function
  - Updated `execute()` to handle modules
  - Updated `generate_worker_module()` with imports/exports
  - Updated `generate_workerd_config()` with module entries

- **Activation**: `jsexec/src/activation.rs`
  - `JsExec::new()` copies modules to `RunnerConfig`

- **Exports**: `jsexec/src/lib.rs`
  - Public exports: `ModuleConfig`, `ModuleSource`

### Integration with Substrate

In `substrate/src/builder.rs`:
```rust
// Initialize JsExec for JavaScript execution in V8 isolates
let jsexec = JsExec::new(JsExecConfig::default());
```

Currently uses default config (no preloaded modules). To add modules:
```rust
let jsexec_config = JsExecConfig {
    modules: vec![
        ModuleConfig::inline("utils", include_str!("utils.js"))
            .with_global(true),
    ],
    ..Default::default()
};
let jsexec = JsExec::new(jsexec_config);
```

### Execution Flow

1. **Config Setup** (activation creation)
   ```
   JsExecConfig { modules: [...] }
   → RunnerConfig { modules: [...] }
   ```

2. **Per-Execution** (when code runs)
   ```
   For each module config:
     - Resolve to ResolvedModule (read file if needed)
     - Write module to temp dir as {name}.js

   Generate worker.js:
     - Add import statements
     - Add globalThis assignments
     - Add ctx.modules object

   Generate config.capnp:
     - List all module entries

   Spawn workerd with temp dir
   ```

3. **User Code Execution**
   ```
   User code sees:
     - ctx.modules.{name}
     - globalThis.{name} (if exposed)
   ```

## Usage Examples

### Example 1: Inline Utility Module

```rust
use jsexec::{JsExec, JsExecConfig, ModuleConfig};

let config = JsExecConfig {
    modules: vec![
        ModuleConfig::inline("utils", r#"
            export function add(a, b) { return a + b; }
            export function multiply(a, b) { return a * b; }
            export default { add, multiply };
        "#).with_global(true),
    ],
    ..Default::default()
};

let jsexec = JsExec::new(config);

// User executes:
// return utils.add(10, 20);  // via globalThis
// return ctx.modules.utils.add(10, 20);  // via ctx
```

### Example 2: File-Based Module

```rust
let config = JsExecConfig {
    modules: vec![
        ModuleConfig::from_file("typescript", "/path/to/typescript.bundle.js"),
    ],
    ..Default::default()
};

let jsexec = JsExec::new(config);

// User executes:
// const ts = ctx.modules.typescript;
// return ts.transpile('const x: number = 42;');
```

### Example 3: Multiple Modules

```rust
let config = JsExecConfig {
    modules: vec![
        ModuleConfig::inline("math", "export const PI = 3.14159;")
            .with_global(true),
        ModuleConfig::inline("string", r#"
            export function reverse(s) { return s.split('').reverse().join(''); }
        "#),
    ],
    ..Default::default()
};

// User code can mix access patterns:
// console.log(math.PI);  // globalThis
// console.log(ctx.modules.string.reverse("hello"));  // ctx.modules
```

## Performance Considerations

### Module Resolution Overhead

- **File-based modules**: Read once per execution (async I/O)
- **Inline modules**: No overhead, code already in memory
- Resolution happens in parallel with other setup tasks

### Workerd Startup

- Each module adds one entry to Cap'n Proto config
- Each module written as separate file in temp dir
- Minimal impact on workerd startup time (modules embedded at config parse time)

### Memory

- Modules duplicated per execution (ephemeral process model)
- For frequently-used large modules, consider:
  - Process pooling (not yet implemented)
  - Caching resolved module content in memory

## Security Considerations

1. **Module Source Validation**
   - File paths are resolved at execution time
   - No sandboxing of file reads (trusted config only)
   - Consider restricting allowed paths in production

2. **Code Injection**
   - Modules are embedded directly in workerd config
   - Same security model as user code
   - V8 sandboxing applies to all code

3. **globalThis Pollution**
   - Only expose modules on globalThis when explicitly configured
   - Avoids namespace conflicts with user code

## Design Rationale

### Why Embedded Modules?

**Alternatives considered**:
1. **Persistent worker pool** - Complexity of state management, less isolation
2. **Dynamic imports at runtime** - Requires network access or FS access in worker
3. **Eval-based loading** - Security concerns, less performant

**Chosen approach**: Embed at spawn time
- Maintains ephemeral isolation model
- Clean teardown after execution
- Workerd native module system (ES modules)
- No dynamic code generation

### Why Two Access Patterns?

1. **`ctx.modules.*`** - Explicit, namespaced, no conflicts
   - Recommended for most use cases
   - Clear where modules come from

2. **`globalThis.*`** - Convenient for common utilities
   - Opt-in via `expose_global`
   - Useful for frequently-used libraries (lodash, etc.)

Users can choose based on their needs.

### Why Builder Pattern?

```rust
ModuleConfig::inline("name", code).with_global(true)
```

- Ergonomic API
- Sensible defaults (expose_global = false)
- Easy to extend with future options
- Fluent interface

## Conclusion

The jsexec module loading system enables sharing JavaScript libraries across ephemeral V8 executions while maintaining the clean isolation model. Modules are resolved once per execution and embedded in the workerd configuration, providing native ES module support with optional globalThis exposure.

The implementation is production-ready with comprehensive tests. Future enhancements could include module caching, NPM package support, and TypeScript transpilation.
